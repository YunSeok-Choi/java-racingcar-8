# java-racingcar-precourse

## 단계별 구현 체크리스트
- [x] 1단계 입력 처리: 콘솔에서 이름 목록과 이동 횟수를 입력받고, 입력 전담 클래스를 분리해 안내 문구 상수와 함께 관리한다.
- [x] 1단계 검증 & 테스트: 이름 길이/구성, 빈 값, 이동 횟수의 양의 정수 여부를 검증하고, 해당 로직을 JUnit + AssertJ 테스트로 즉시 검증한다.
- [x] 2단계 도메인 구성: `Car`, `RaceParticipants` 등 경주 관련 도메인 객체를 정의하고 생성 시점에 검증 로직을 통합한다.
- [x] 2단계 초기화 & 테스트: 유효한 입력으로 자동차 컬렉션을 초기화하고, 초기 상태(위치 0 유지 등)를 단위 테스트로 확인한다.
- [x] 3단계 난수 전략 추상화: `Randoms.pickNumberInRange(0, 9)` 호출을 감싼 인터페이스/전략 클래스를 만들고, 테스트 더블을 이용한 검증 테스트를 작성한다.
- [x] 3단계 라운드 진행 & 출력: 라운드별 전진 판단과 결과 출력을 도메인/뷰로 분리하고, 라운드 진행 로직에 대한 테스트를 추가한다.
- [x] 4단계 우승 계산 & 테스트: 최종 우승자 산출 로직을 별도 객체나 메서드로 분리하고, 단독/공동 우승 시나리오 테스트를 구현한다.
- [x] 4단계 최종 출력 정리: "최종 우승자 : {winner(s)}" 포맷을 상수화하고, 출력 전담 클래스에서 결과 문자열을 생성하도록 만든다.
- [x] 5단계 예외 전파 정책: 입력 단계 예외를 상위로 전파해 애플리케이션이 자연스럽게 종료되도록 확인하고, 예외 케이스 테스트를 유지한다.
- [x] 5단계 구조 다듬기: 도메인, 입력, 출력, 애플리케이션 구성을 패키지 레벨에서 분리하고 객체 간 의존을 점검한다.

## 예외 상황 및 방침
- 비어 있거나 공백뿐인 이름 입력은 허용하지 않고 즉시 예외를 발생시킨다.
- 이름 목록에 빈 항목이 포함될 경우(예: `pobi,,woni`)도 허용하지 않는다.
- 이동 횟수 입력이 숫자 이외의 문자(예: "three" 혹은 공백)를 포함할 경우 예외를 발생시킨다.
- 난수 생성은 미션에서 제공하는 `camp.nextstep.edu.missionutils.Randoms`만 사용한다.

## 테스트 전략
- 경계값 테스트 : 이름 길이(1자, 5자)와 이동 기준값(3, 4) 근처에서 동작을 검증한다.
- 예외 테스트 : 잘못된 이름, 음수 이동 횟수, 비정수 입력에 대해 `IllegalArgumentException`이 발생하는지 확인한다.
- 우승자 계산 테스트 : 공동 우승, 단독 우승, 모든 차량 동일 거리 등 다양한 시나리오를 포함한다.
- 단위 vs. 통합 테스트 : 도메인 로직은 단위 테스트로 검증하고, 입출력은 필요 시 캡슐화된 래퍼를 이용해 최소한으로 검증한다.

## 도전 과제
- 난수 생성 로직을 인터페이스로 추상화해 테스트 환경에서 고정 값으로 주입하는 구조를 설계한다.
- 게임 진행 중간 상태를 기록하는 `RaceRound`를 도입해 라운드별 결과를 객체로 관리해 본다.
- 객체지향이나 클린 아키텍처 등 익숙하지 않은 구조를 실험적으로 적용해 책임을 명확히 분리해 본다.

### 프로그래밍 요구 사항 1
 - JDK 21 버전에서 실행 가능해야 한다. 
 - 프로그램 실행의 시작점은 Application의 main()이다. 
 - build.gradle 파일은 변경할 수 없으며, 제공된 라이브러리 이외의 외부 라이브러리는 사용하지 않는다. 
 - 프로그램 종료 시 System.exit()를 호출하지 않는다. 
 - 프로그래밍 요구 사항에서 달리 명시하지 않는 한 파일, 패키지 등의 이름을 바꾸거나 이동하지 않는다. 
 - 자바 코드 컨벤션을 지키면서 프로그래밍한다. 
 - 기본적으로 Java Style Guide를 원칙으로 한다.

### 프로그래밍 요구 사항 2
 - indent(인덴트, 들여쓰기) depth를 3이 넘지 않도록 구현한다. 2까지만 허용한다. 
   - 예를 들어 while문 안에 if문이 있으면 들여쓰기는 2이다. 
   - 힌트: indent(인덴트, 들여쓰기) depth를 줄이는 좋은 방법은 함수(또는 메서드)를 분리하면 된다. 
 - 3항 연산자를 쓰지 않는다. 
 - 함수(또는 메서드)가 한 가지 일만 하도록 최대한 작게 만들어라. 
 - JUnit 5와 AssertJ를 이용하여 정리한 기능 목록이 정상적으로 작동하는지 테스트 코드로 확인한다.
